## 2. 分层架构

### 2.1 依赖方向（铁律）

```
pages/  ──►  services/  ──►  domain/
   │            │              ▲
   │            └──► mock/ ─────┘（mock 复用 domain 纯函数）
   ├──►  components/chart/
   ├──►  store/
   └──►  platform/
```

**三条不可越界的规则**：

1. `domain/` 是**纯函数层** —— 不 import Taro、不 import React、不碰 UI。可被 `scripts/selftest.ts` 直接在 Node 里跑。
2. `services/` 只做 HTTP —— 一端点一函数，页面不得直接调 `client`。
3. `pages/` 只做编排 —— 不写算法。

> 后端用 Python 重写算法时，`domain/` 的每个函数都可逐条对照验收。
> **✅ 这一步已经完成并被机器验证** —— 见 `docs/02-接口契约.md` §6.1。

### 3.2 `domain/methods.ts` —— 11 种方式元数据

内置：手冲 V60 / Kalita / Origami、Chemex、法压壶、虹吸壶、摩卡壶、意式浓缩、爱乐压、气压壶 FP-1、冷萃。

| 导出 | 说明 |
|---|---|
| `BREW_METHODS` | 方式数组（由内部 `RAW_METHODS` 归一化而来） |
| `METHOD_MAP` | `id → BrewMethod` 索引 |
| `findMethod(idOrAlias)` | 按 id 或别名查找（别名如「手冲」「意式」「浓缩」） |
| `getFlavorBaseline(methodId)` | 取方式的六轴目标基线 |
| `calcRatio({doseGrams, waterGrams})` | 粉液比 = 水量 ÷ 粉量，保留 2 位小数 |
| `validateParams(methodId, params)` | 逐参数按 `ParamSpec.range` 判定，返回越界项 `{field, label, value, range, severity}`；偏离区间跨度 > 25% 记 `error`，否则记 `warn`。跳过无 `range` 与 `derived` 的参数（如 `ratio`） |

| `matchScore(actual, baseline)` | 吻合度 0–100：`100 − (六轴绝对差之和 / 6) × 20`，钳制在 0–100。与基线完全一致 = 100，每轴平均差 5 分即为 0 |

### 3.4 `domain/curve/interpolate.ts` —— 单调三次样条

Fritsch–Carlson 单调三次插值。

- **为什么不用普通三次样条**：普通样条在数据点之间会过冲，冲煮曲线「重量只增不减」的物理约束会被破坏，出现负流速。单调版本在斜率变号处把切线置 0，杜绝过冲。
- `monotoneCubicInterp(x0,y0,x1,y1,m0,m1,samples)`：区间内采样。
- `smoothCurve(points, interval = 1)`：整体插值，按 `interval` 秒采样。点少于 2 个时原样返回。

### 3.5 `domain/curve/generate.ts` —— 冲煮曲线

三种来源统一为 `CurveSource`：

| 模式 | 函数 | 生成规则 |
|---|---|---|
| `plan` | `generatePlanCurve(steps, totalSeconds)` | 注水计划 → 关键点 → 单调样条平滑 → 差分求流速 → 阶段着色 |
| `keypoint` | `generateKeypointCurve(keypoints, stages?)` | 用户打的关键点（时刻+累计重量）→ 排序 → 平滑 → 补阶段 |
| `device` | `cleanDeviceCurve(raw)` | 原始序列 → 剔除累计重量倒退噪点 → 流速窗口放宽到 5 |

关键实现口径：

- **注水动作时长**：`POUR_DURATION = 8` 秒。首段（`atSecond === 0`）视为一次快速注水动作，用 8 秒表现这段重量上升，而非瞬间跳变。
- **瞬时流速** `computeFlow(points, window = 3)`：`flow = Δw / Δt`，负值截为 0，再用窗口滑动平均抹掉称重抖动。
- **阶段推导** `deriveStages(steps, totalSeconds)`：由相邻注水步骤的时间点切段，最后一段延伸到 `totalSeconds`。
- **阶段判定** `stageAt(stages, t)`：遍历区间，**返回第一个包含 `t` 的区间**；都不命中时回退到最后一个区间的阶段。
- **统计** `curveStats(curve)`：`duration` / `finalWeight` / `avgFlow` / `peakFlow`。

### 3.6 `domain/curve/roast.ts` —— 烘焙曲线

| 导出 | 口径 |
|---|---|
| `computeRoR(points, windowSeconds = 30)` | `RoR = dBT/dt × 60`（℃/min）。**取窗口内最早的可用点做差分**（后向窗口，非中心差分），再叠 3 点加权平滑 `(prev + 2v + next) / 4` 去尖刺 |
| `computeDTR(events, totalSeconds)` | `(drop.atSecond − firstCrack.atSecond) / totalSeconds × 100`（发展比） |
| `computeWeightLoss(green, out)` | `(1 − out / green) × 100` |
| `computePhaseRatio(events, totalSeconds)` | 脱水 / 梅纳 / 发展三段时长占比（%） |
| `computeRoastMetrics(batch)` | 一次算全上述指标 |
| `checkRorShape(points, events)` | RoR 形态健康检查（crash 骤降 / flick 尖刺 / 一爆前热量不足） |
| `roastPhaseAt(t, events)` | 按事件判定所处烘焙阶段 |
| `generateRoastCurve(events, ...)` | 由事件合成理论 BT/ET/RoR 曲线 |
| `roastCurveStats(points)` | 峰值豆温、峰值 RoR 等统计 |
| `parseArtisanAlog(text)` | 解析 Artisan `.alog`，返回 `{points, events, warnings}`，缺事件时给出 warning |

> ⚠️ `checkRorShape` / `parseArtisanAlog` / `computeRoR`（直接调用）目前**没有页面调用**，见第 12 章。

### 3.7 `domain/diagnosis/index.ts` —— ★ 风味偏差诊断

纯函数，输入「方式 + 风味画像」，输出诊断。这是产品的差异化核心。

**偏差计算** `computeDeviations(actual, baseline)`：逐轴算差值，**只保留 |Δ| ≥ 2 的轴**，按偏差绝对值降序。

**判定** `diagnose(method, flavor)`，按顺序判定：

| 判定 | 条件 | 文案 |
|---|---|---|
| `flat` | 六轴**全部** ≤ 基线 − 2 | 风味平淡 |
| `uneven` | 酸 ≥ +2 **且** 甜 ≥ +2 **且** 平衡 ≤ − 2 | 萃取不均 |
| `under_extracted` | `1.2×Δ酸 − Δ甜 − 0.5×Δ平衡 ≥ 2` | 萃取不足 |
| `over_extracted` | `0.8×Δ醇厚 − Δ平衡 − 0.8×Δ余韵 ≥ 2` | 萃取过度 |
| `ok` | 以上都不满足 | 表现正常 |

**处方** `buildPrescriptions(verdict, method, flavor)`：按判定产出带优先级的处方列表（`priority` 按产出顺序自增）。

| 判定 | 处方序列（按优先级） |
|---|---|
| 欠萃 | 研磨调细（1–2 格）→ 增加粉量（粉水比上调 0.5）→ 提高水温（+2℃）→ 延长萃取时间（+10s）→〔仅重力渗透〕加强搅拌与注水 →〔仅意式〕考虑换豆或加深烘焙 |
| 过萃 | 研磨调粗（1–2 格）→ 缩短萃取时间（−10s）→ 降低水温（−2℃）→ 减缓注水 |
| 不均 | 改善搅拌均匀度 → 检查熟豆新鲜度与细粉 → 适当增加粉量（+1g） |
| 平淡 | 提高粉水比（收紧 1）→ 提高水温（+2℃） |
| 正常 | 保持当前配方 → 下一杯只改一个变量（建议从研磨度开始） |

**缺陷触发的补充处方**（在上述序列之后追加）：

| 触发条件 | 追加处方 |
|---|---|
| 缺陷含 `burnt`（焦糊）或 `smoky`（烟熏） | 检查烘焙曲线 |
| 缺陷含 `papery`（纸板味）或 `woody`（木质） | 检查豆子新鲜度 |

> ⚠️ **代码缺陷**：`FLAVOR_DEFECTS`（风味页缺陷 chips 的数据源）只含 `papery` / `moldy` / `phenolic` /
> `fermented_boozy` / `rubbery` / `grassy` / `quakery` 七项，**不含 `burnt` / `smoky` / `woody`** ——
> 这三个 id 只存在于风味轮描述词里。因此「检查烘焙曲线」这条处方**在真实 UI 链路中不可达**，
> 只有 `papery` 一条能触发「检查豆子新鲜度」。修复方向见 §12 P1-6。

## 4. 数据与状态层

### 4.1 传输层抽象 `services/http.ts`

```ts
interface Transport { request<T>(options: RequestOptions): Promise<T> }
```

- `mockTransport`（在 `src/mock/db.ts`）与 `realTransport`（在 `http.ts`）**签名完全一致**，由 `TARO_APP_API_MODE` 在 `services/index.ts` 里二选一。
- `realTransport` 行为：
  - `BASE_URL` = `TARO_APP_API_BASE_URL` 或 `http://127.0.0.1:8000/api/v1`
  - 自动拼 query（跳过 `undefined`/`null`/`''`）
  - 自动带 `Authorization: Bearer <token>`，token 存 `Taro.setStorageSync('ppcoffe.token')`
  - 解析统一包络 `{ok, data, error, meta}`，非 2xx 或 `ok === false` 抛 `ApiRequestError`（携带 `code` / `details` / `field`）
  - 默认超时 15 秒
- `HttpClient` 对外只有 4 个方法：`get` / `post` / `patch` / `del`。

## 5. 跨端适配层

### 5.1 `platform/chartContext.ts` —— Canvas 上下文

统一接口 `ChartContext`（`setStrokeStyle` / `beginPath` / `moveTo` / `lineTo` / `stroke` / `arc` / `fillText` / `fillRect` / `setLineDash` 等），两套实现：

| 端 | 实现 |
|---|---|
| 小程序 | `TaroChartContext` —— 包装 Taro/微信旧版 `CanvasContext`；`setFontSize` 直接写 `font` 属性（微信原生支持，避开 H5 端该方法的坑） |
| H5 | 原生 `CanvasRenderingContext2D` 直接取用 |

**背景**：Taro H5 的 `Canvas` 组件把 `canvas-id` 挂在包装元素 `<taro-canvas-core>` 上，内层 `<canvas>` 没有该属性，`Taro.createCanvasContext()` 在 H5 端按 `canvas[canvas-id]` 查询会找不到节点（**静默失效，画布全白**）。`process.env.TARO_ENV` 会被构建期常量替换，H5 分支在小程序包里被完全剔除。

### 5.2 `platform/image.ts` —— 选图

`pickImages(count)` / `readImageAsDataUri(path)` / `guessExtension(path)`，抹平两端选图 API 差异，返回 `PickedImage { path, size }`。`readImageAsDataUri` 供 mock 模式把图片转成 data URI 直传。

### 5.3 跨端踩坑备忘（写图表组件前必读）

| 坑 | 现象 | 处理 |
|---|---|---|
| `canvas-id` 挂错节点 | H5 端画布全白且无报错 | 见 §5.1 |
| `setFontSize` 依赖已设置字体族 | 抛 `Cannot read properties of undefined (reading 'split')` | 封装层统一处理字体 |
| Canvas 每次渲染重设 `canvas.width/height` | 父组件重渲染后画布被清空变白 | **每次渲染后都重绘**，且取不到上下文时按帧重试（≤30 次） |
| `useReady` 在子组件中不触发 | 图表组件不渲染 | 不用 `useReady`，改挂载后自行重试 |

## 6. 组件层

`src/components/chart/` 共 3 个组件，全部是 **Canvas 自绘，零图表依赖**。

### 6.1 `CurveChart` —— 冲煮曲线

```ts
interface CurveChartProps {
  points: CurvePoint[]
  stages?: CurveStageSpan[]      // 阶段色带
  height?: number                 // 默认 240
  showFlow?: boolean              // 叠加瞬时流速次轴
  overlays?: { label: string; points: CurvePoint[]; color?: string }[]  // 对比曲线
}
```

绘制顺序：阶段色带（8% 透明度）→ 网格与 Y 轴刻度（`{v}g`）→ X 轴时间刻度（`{t}s`）→ 对比曲线（先画，压在主曲线下，透明度 0.75）→ 流速次轴（**与主曲线同底**，量程只占绘图区**下半 50%** 高度，`v=0` 在底边、`v=max` 在中线）→ 主曲线（2px）→ 终点圆点。

### 6.2 `RoastCurveChart` —— 烘焙曲线（BT / ET / RoR 三通道）

```ts
interface RoastCurveChartProps {
  points: RoastCurvePoint[]    // { t, bt, et, ror }
  events: RoastEvent[]         // 事件标记（投豆 / 回温点 / 脱水结束 / 一爆 / 下豆）
  height?: number              // 默认 280
  overlays?: { label: string; points: RoastCurvePoint[]; color?: string }[]
}
```

三通道分工：**BT 豆温**为主曲线（信号色，粗）、**ET 环境温**为次曲线（琥珀色，细）、**RoR 升温率**走副轴（危险色，细）。另叠加脱水 / 梅纳 / 发展三段阶段色带与事件标记。

### 6.3 `FlavorRadar` —— 风味雷达（★ 差异化核心图形）

```ts
interface FlavorRadarProps {
  actual: FlavorAxes     // 本次实测
  baseline: FlavorAxes   // 该方式的目标基线
  size?: number          // 默认 280
}
```

同时画两条轮廓：**基线为虚线**、**实测为实心填充（14% 透明度）**，叠加差值即风味偏差。4 圈网格 + 6 条轴线 + 顶点色点 + 轴标签（`size/2 − 44` 为半径）。

### 6.4 图表配色 `styles/colors.ts`

Canvas 读不到 CSS 变量，因此**单独维护一份与 `themes.scss` 对应的调色板**（`chartPalette(theme)`），字段：`line` / `lineStrong` / `text` / `textDim` / `textMute` / `signal` / `amber` / `danger` / `ok` / `stage{}`（四个阶段色）/ `axis[]`（6 轴色）。

| # | 缺口 | 影响 |
