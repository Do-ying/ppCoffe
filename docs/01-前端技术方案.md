## 2. 候选方案对比

### 方案 A：Taro 4 + React 18 + TypeScript（跨端）

| 维度 | 评价 |
|---|---|
| 覆盖端 | 微信小程序 ✅ / H5 ✅ / 支付宝 / 抖音小程序 ✅ / RN（可选）✅ |
| 交互性能 | React 渲染在小程序有 `setData` 开销，需规避；但 Canvas 绘制不受影响 |
| 曲线能力 | `@antv/f2` 5.x 原生支持 React，Canvas/SVG 双渲染，**支持自定义 annotation**（阶段染色、事件 marker）✅ |
| 包体积 | 需按需引入 + 分包；Taro 4 运行时比原生大 |
| 生态/人才 | React + TS 人才最多，后端 Python 团队也最熟；OpenAPI codegen 支持最完善 ✅ |
| 痛点 | 小程序端 React 状态更新频繁会卡；需用 store 直接订阅而非 props 透传 |

### 方案 B：uni-app (Vue3) + TypeScript + uCharts

| 维度 | 评价 |
|---|---|
| 覆盖端 | 微信小程序 ✅ / H5 ✅ / App ✅（uni-app x 编译到原生，性能更好） |
| 交互性能 | Vue3 响应式在 uni-app 编译下表现稳定，小程序端优于 React ✅ |
| 曲线能力 | **uCharts 是国内跨端图表生态最成熟方案**，Canvas 渲染、体积小、自定义标记能力强 ✅✅ |
| 包体积 | 同体积控制良好 ✅，分包支持成熟 |
| 生态/人才 | Vue + TS 人才多；Pinia 状态管理成熟 ✅ |
| 痛点 | 图表定制上限略低于 F2/ECharts；App 端有历史包袱（需选 uni-app x） |

### 方案 C：微信小程序原生 + Skyline + TypeScript

| 维度 | 评价 |
|---|---|
| 覆盖端 | 仅微信小程序 ❌（H5 需另写一套） |
| 交互性能 | **天花板**，Skyline 原生渲染 + Canvas 2D ✅✅ |
| 曲线能力 | 全部自研（Canvas 2D 手绘曲线），工作量最大 |
| 包体积 | 最小 ✅✅ |
| 痛点 | 工程化弱、无组件生态、只服务微信、图表自研成本高 |

### 方案 D：纯 Web（React + Vite + PWA + Capacitor）

| 维度 | 评价 |
|---|---|
| 覆盖端 | Web/PWA ✅ / iOS·Android App（Capacitor）✅ / 微信小程序 ❌ |
| 交互性能 | 最好，浏览器原生 ✅✅ |
| 曲线能力 | ECharts / Recharts / D3 全部可用，定制最自由 ✅✅ |
| 痛点 | 微信生态（分享卡片、扫码、登录、订阅消息）全部拿不到，与「小程序」诉求冲突 |

## 3. 推荐

### 🥇 首选：**方案 A — Taro 4 + React 18 + TypeScript**

**理由**：
1. **一石多鸟**：小程序与 H5 一次开发。H5 用于「分享链接 + 手机扫码验收 + 搜索引擎收录」，小程序用于主战场
2. **曲线是本产品的心脏**，React + F2 的自定义标注能力最强（阶段染色、事件 marker、多线叠加、Brush 刷选）
3. **后端大概率是 Python**：OpenAPI → TS 类型自动生成链路最顺（`openapi-typescript`），契约不会漂移
4. **React + TS 招聘与协作成本最低**，也最匹配本次已安装的 frontend-design / frontend-dev 两个 skill 的产出形态
5. 跨端抽象只需一个 `platform` adapter 层，业务代码零平台分支

### 🥈 备选：**方案 B — uni-app + uCharts**

**如果**：团队以 Vue 为主、或明确要同时出 App（用 uni-app x）、或更看重小程序包体积与渲染稳定性。
**代价**：曲线深度定制时 uCharts 的能力边界比 F2 略窄；React 生态里的曲线交互库（如 visx、d3-shape）用不上。

### 🥉 兜底：**方案 C — 原生小程序**

**如果**：确定只做微信小程序且要求极致流畅，并且愿意自研 Canvas 曲线渲染层。
**代价**：H5 完全落空（分享/验收都要另想办法），图表自研约占 P2 阶段 40% 工时。

### 4.3 关键设计

**① 曲线渲染：自研 Canvas 2D（落地实况，未引入 F2）**

> **原方案**：F2 为主 + Canvas 补充层。**实际落地为完全自研 Canvas**，F2 未引入。
> 原因：曲线所需能力（阶段色带、事件标记、多线叠加）高度定制，F2 的定制收益不抵其体积与接入成本；
> 且曲线本质是「折线 + 圆角 + 文字」，Canvas 2D 自绘完全够用，同时天然规避小程序包体积问题。

```tsx
// 实际组件签名（src/components/chart/CurveChart.tsx）
<CurveChart
  points={[{ t, w, flow, stage }]}                    // 曲线点
  stages={[{ from, to, label, stage }]}                // 阶段色带（闷蒸/萃取/滴滤）
  height={240}
  showFlow={true}                                     // 叠加瞬时流速次轴
  overlays={[{ label, points, color }]}                // 对比曲线
/>
```

- 阶段染色：8% 透明度色块，按 `CurveStageSpan` 区间填充。
- 对比曲线：`overlays` 先画（透明度 0.75），压在主曲线下方。
- **跨端上下文**：`platform/chartContext.ts` 统一封装 —— H5 端取原生 `CanvasRenderingContext2D`，小程序端用 Taro 旧版 `CanvasContext`，绘图代码零分支。
- **重绘时机**：每次渲染后都重绘（取不到上下文时按帧重试 ≤30 次）。原因：Taro H5 的 Canvas 每次渲染会重设 `canvas.width/height` 从而清空画布；且 `useReady` 在子组件中不触发，不能依赖。
- ⚠️ **未实现**：长按读数 tooltip、双指缩放、滑动切换 overlay —— 曲线目前是纯展示，无交互读数。

**② 实时计时器（❌ 未实现）**

> 原方案的 `useTimer` / `useKeepAwake` / `useBluetoothScale` 三个 hook **均未建立**（`hooks/` 目录不存在）。
> 当前曲线只能来自 `plan`（注水计划生成的理论曲线）；`keypoint` 与 `device` 两种来源的算法已实现
> （`generateKeypointCurve` / `cleanDeviceCurve`），但**没有页面调用**。

**③ 风味偏差诊断（✅ 已实现于 `domain/diagnosis/`）**

```ts
type Diagnosis = {
  matchScore: number            // 0-100，与方式风味基线的吻合度
  deviations: Deviation[]       // 哪一轴偏了、偏多少（仅保留 |Δ| ≥ 2）
  verdict: 'under_extracted' | 'over_extracted' | 'uneven' | 'flat' | 'ok'
  prescriptions: Prescription[] // 带优先级的处方（改什么）
}
```
纯函数，输入 `method + flavorProfile`，输出诊断。已接入风味页与详情页实时渲染；判定与处方规则见 `docs/03` §3.7。

**④ Mock 与真后端切换（✅ 已实现）**

```
httpClient → httpTransport
  ├── mockTransport   # src/mock/db.ts：内存 DB + 真实 CRUD/筛选行为
  └── realTransport   # src/services/http.ts：Taro.request → baseURL + Authorization
```
通过 `TARO_APP_API_MODE=mock|real` 环境变量或设置项切换。前端开发全程用 mock，后端就绪后只改环境变量。
**⚠️ 现状**：real 模式下 `Authorization` 头已有实现，但**尚无登录流程写入 token**，因此带鉴权的请求会缺失头部（见 `docs/03` §12 的 P0-3）。

**⑤ 包体积控制**

- 主包只放：首页、记录列表、豆仓列表、核心通用组件
- **分包**：`brew-curve`、`roast`、`settings` 各自分包（**尚未配置，当前 14 页全部在主包**）
- 图表库按需引入，字体文件不进包（走 CDN 或用系统字体栈）
- ✅ 实际收益：自研 Canvas 图表层**零依赖**，是当前包体积最小的关键决策

### 4.4 设计方向（frontend-design skill 介入点）

本项目视觉要避开「AI 味」和「咖啡 App 同质化」——现在市面上的咖啡 App 几乎都是米色背景 + 棕色 + 圆角卡片 + 一杯咖啡图。

**建议方向**：
- **仪器感**：把「曲线 + 数据 + 刻度」当成主体，视觉参考示波器/飞行仪表盘，而非生活方式 App
- **色板**：深炭黑底（`#141414` 系）+ 单一暖色强调（如烘焙橙 `#D97757` 属 frontend-design 点名的 AI 套路，需换），建议用 **青灰 + 琥珀** 双色，或 **纸张白 + 墨黑 + 单一荧光绿**（示波器语义）
- **字体**：数字与标签用等宽体（曲线读数需要等宽对齐），标题用有性格的 grotesque 或衬线；**不用 Inter**
- **结构**：信息密度高但有秩序；用发丝线与网格对齐，不用一排同款圆角卡片
- **动效**：只做一处记忆点（如曲线绘制的生长动画），其余克制

具体执行时用 `frontend-design` skill 的两段式工作法：先出 token 方案 + ASCII 线框 → 对照需求复审唯一性 → 再写代码。

**落地实况（✅ 已实现）**：

| 项 | 实际取值 |
|---|---|
| 仪器感 | ✅ 图表是主体：曲线 + 雷达 + 刻度 + 网格；页面区块用发丝线（`--line`）分隔 |
| 色板 | ✅ **深炭墨底 `#0d0f0e` + 仪表荧光青 `#7fd1c1` + 琥珀 `#e9b44c`**（**已弃用烘焙橙 `#D97757`**）；另提供浅色主题 `#f2f4f2` + `#0e8a78` |
| 主题 | ✅ **双主题 + 跟随系统**，全部落在 CSS 变量；Canvas 另维护一份对应调色板（`styles/colors.ts`） |
| 字体 | ✅ `--font-mono` 等宽栈用于数值读数，`--font-sans` 用系统栈（**未引 Inter，未引 webfont**） |
| 圆角 | ✅ 克制：`--r-sm/md/lg` = 4/10/20 rpx |
| 动效 | ❌ 尚未实现曲线生长动画 |

> **两处刻意决定**：
> 1. 浅色主题**不是深色的反相**，而是独立的「冷灰白纸感 + 压暗信号青」，保持同一套仪表语言。
> 2. Canvas 读不到 CSS 变量，因此 `styles/colors.ts` 必须与 `themes.scss` **手动保持同步** —— 改主题色时两处都要改。

## 5. 决策点
