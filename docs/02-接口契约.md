# ppCoffe · 后端接口契约（草案 v0.1）

> 面向后端实现（当前设想 Python，但契约与语言无关）。
> 前端已内置 Mock 层，**后端未就绪不阻塞前端开发**；后端就绪后仅需切换 `baseURL`。
> 建议后端直接产出 OpenAPI 3.1 文档，前端用 `openapi-typescript` 生成类型，杜绝契约漂移。

## 1. 通用约定

### 1.1 基础

| 项 | 约定 |
|---|---|
| Base URL | `https://{host}/api/v1`（本地 `http://127.0.0.1:8000/api/v1`） |
| 传输 | HTTPS + JSON，`Content-Type: application/json; charset=utf-8` |
| 认证 | `Authorization: Bearer <token>`；微信小程序用 `wx.login` code 换 token |
| 时间 | ISO 8601 带时区，UTC 存储，前端按本地时区展示 |
| 重量/体积 | 一律 **gram（g）** 存整数毫克（mg）防浮点误差；ml 仅作展示换算 |
| 温度 | 摄氏度，保留 1 位小数 |
| 时长 | **秒（整数）** |
| 坐标 | 曲线点 `{ t: 秒, w: 毫克 }`；流量 `{ flow: 毫克/秒 }` |

### 1.2 统一响应包络

成功：
```json
{ "ok": true, "data": { ... }, "meta": { "requestId": "req_01H..." } }
```

失败：
```json
{
  "ok": false,
  "error": {
    "code": "BREW_PARAM_OUT_OF_RANGE",
    "message": "粉液比超出该方式的推荐区间",
    "details": { "ratio": 1.28, "recommended": [1.13, 1.18] },
    "field": "dose"
  },
  "meta": { "requestId": "req_01H..." }
}
```

### 1.3 错误码

| code | HTTP | 含义 |
|---|---|---|
| `INVALID_PARAM` | 400 | 参数不合法 |
| `VALIDATION_FAILED` | 422 | 语义校验失败（如粉液比越界、曲线点数不足） |
| `UNAUTHORIZED` | 401 | 未登录 / token 失效 |
| `FORBIDDEN` | 403 | 无权访问该记录 |
| `NOT_FOUND` | 404 | 资源不存在 |
| `CONFLICT` | 409 | 重复资源（如同一 bean 下批次号重复） |
| `RATE_LIMITED` | 429 | 频率限制 |
| `INTERNAL` | 500 | 服务端异常 |

### 1.4 分页与排序

列表统一使用游标分页（曲线数据量大，offset 会退化）：

**请求**
```
GET /api/v1/brews?cursor=<opaque>&limit=20
```
**响应**
```json
{
  "ok": true,
  "data": { "items": [ ... ] },
  "meta": {
    "pagination": { "nextCursor": "eyJ0IjoiMjAyNi0xMS0yM1QxMDowMDowMFoifQ", "hasMore": true, "limit": 20 },
    "requestId": "req_01H..."
  }
}
```
排序参数统一 `?sort=-brewDate,createdAt`（`-` 前缀表示降序）。

## 4. 关键端点详解

### 4.1 `POST /brews/derive-curve` ★ 由参数生成曲线

前端可本地生成，但**后端也应提供同一实现**作为权威口径（用于跨端一致与校验）。

**请求**
```jsonc
{
  "method": "pour_over_v60",
  "mode": "plan",              // plan | keypoint
  "params": {
    "doseGrams": 15, "waterGrams": 250,
    "temperature": 93, "brewSeconds": 165
  },
  "steps": [
    { "atSecond": 0,  "toGrams": 45 },
    { "atSecond": 45, "toGrams": 170 },
    { "atSecond": 90, "toGrams": 250 },
    { "atSecond": 165,"toGrams": 250 }
  ],
  "keypoints": null            // mode=keypoint 时传 [{t, w}]
}
```

**响应**
```jsonc
{
  "ok": true,
  "data": {
    "points": [ { "t": 0, "w": 0, "flow": 0, "stage": "bloom" } ],
    "stages": [
      { "from": 0,   "to": 45,  "label": "闷蒸",  "stage": "bloom" },
      { "from": 45,  "to": 165, "label": "萃取",  "stage": "extraction" },
      { "from": 165, "to": 165, "label": "滴滤完成","stage": "drawdown" }
    ],
    "meta": { "generator": "monotone-cubic-v1", "pointCount": 180 }
  }
}
```

### 4.2 `GET /brews/{brewId}/diagnosis` ★ 风味偏差诊断

## 5. Mock 策略

后端未就绪时，前端用本地内存 DB 模拟上述全部端点。**实际落地形态**（与原计划的 JSON fixtures 目录不同）：

```
src/mock/
└── db.ts                 # ★ 单一文件：内存 DB + Mock Transport + 内联 fixtures
    ├── beanFixtures      #   3 支豆
    ├── 冲煮记录 fixtures  #   曲线由 generatePlanCurve 现场合成
    ├── 烘焙批次 fixtures
    └── mockTransport     #   按 URL 前缀 + method 分发，列表按 query 真实过滤
```

- `mockTransport` 实现与 `realTransport` **完全相同的接口签名**，由 `TARO_APP_API_MODE` 切换
- Mock 支持增删改查与筛选（列表接口按 query 参数真实过滤），因此前端开发体验接近真实后端
- 曲线生成与诊断算法：Mock 模式下**用前端的 `domain/` 纯函数实现**（保证离线可用），真实后端就绪后可切换为调用服务端以验证一致性
- **方式元数据与风味轮词库不走后端**：以本地常量表（`domain/methods.ts` / `domain/flavor.ts`）为准，离线可用、零请求；`GET /methods` 与 `GET /flavor-wheel` 已实现但页面未调用

### 5.5.1 器具 Equipment

冲煮记录会关联「本次用了哪些器具」（磨豆机 / 滤杯 / 手冲壶 / 咖啡机 / 电子秤 / 烘豆机），
其中**磨豆机的刻度基准**是研磨度记录的前提（刻度只在具体某台机器上有意义）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/equipment` | 器具列表，按 type 分组返回 |
| POST | `/api/v1/equipment` | 新增器具 |
| GET | `/api/v1/equipment/{equipmentId}` | 器具详情 |
| PATCH | `/api/v1/equipment/{equipmentId}` | 更新器具 |
| DELETE | `/api/v1/equipment/{equipmentId}` | 删除器具（不影响历史记录） |

```jsonc
// Equipment
{
  "id": "eq_grinder_ek43",
  "type": "grinder",           // grinder|dripper|brewer|espresso|scale|roaster|other
  "name": "EK43",
  "brand": "Fellow",
  "model": "EK43 S",
  "notes": "#22 约 0.8mm，粗细以刻度计",   // 磨豆机刻度基准

}
```

**冲煮记录侧**：`BrewRecord.equipmentIds: string[]`（可关联多件），

  "roaster": "Aillio Bullet R2",
  "greenGrams": 500, "outGrams": 425,
  "weightLossPercent": 15, "totalSeconds": 512,
  "events": [ /* charge / turningPoint / dryEnd / firstCrack / drop */ ],
  "dtrPercent": 32,

    { "t": 0,   "bt": 205, "et": 180, "ror": 0 },

### 5.5.3 图片上传（对象存储由后端决定）

**前端不绑定任何存储实现**（MinIO / S3 / OSS 均可），只消费后端下发的四个字段。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/uploads/presign` | 申请直传目标 |
| POST | `/api/v1/uploads` | 直传兜底（multipart 由后端接收并转存） |
| DELETE | `/api/v1/uploads?objectKey=xxx` | 删除对象 |

**推荐：预签名直传**（图片流量不经过应用服务器）

```jsonc
// POST /api/v1/uploads/presign  →  200
{
  "objectKey": "brew/br_01H8Y/2026-1123-a1b2c3.jpg",
  "uploadUrl": "https://<endpoint>/<bucket>/brew/...?X-Amz-Signature=...",
  "publicUrl": "https://<cdn-or-public>/brew/br_01H8Y/2026-1123-a1b2c3.jpg",
  "headers": { "Content-Type": "image/jpeg" }
}
```

前端流程：`pickImages` → `presign` → `Taro.uploadFile(PUT uploadUrl)` → 用 `objectKey` + `publicUrl` 关联记录。

**冲煮记录侧**：

```jsonc
{
  "images": [
    {
      "id": "img_01H8Z",
      "objectKey": "brew/br_01H8Y/2026-1123-a1b2c3.jpg",
      "url": "https://<public>/brew/br_01H8Y/2026-1123-a1b2c3.jpg",
      "caption": "粉层状态",
      "width": 1200, "height": 1600, "sizeBytes": 284512
    }
  ],
  "review": "这杯整体偏薄……下一杯把研磨调细半格、水温提到 94℃"
}
```

- `review` 评鉴内容（长文本），`flavor.note` 是短风味备注，两者并存
- 图片与评鉴都挂在冲煮记录上，`PATCH /api/v1/brews/{brewId}` 提交

**后端实现建议（MinIO）**：

| 项 | 建议 |
|---|---|
| 桶 | 建议按用途分桶：`ppcoffe-brew`（冲煮图片）、`ppcoffe-roast`（.alog 原文件） |

## 7. 待后端确认的问题

1. 认证方案：只用微信小程序登录，还是也要 Web 端账号/密码？

6. 图片桶用公开读还是私有 + 签名读？私有更安全，但前端展示需要后端下发带签名的 URL 或做一层图片代理。
