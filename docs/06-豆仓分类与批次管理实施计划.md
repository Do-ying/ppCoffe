# ppCoffe 豆仓分类与批次管理实施计划

豆仓新增「购买的成品豆」和「生豆」两种录入方式。成品豆购入后可以直接记录冲煮。生豆按购入批次登记库存，同一批生豆可以分多炉烘焙，每炉单独记录烘焙度、曲线和养豆事件。冲煮时选择实际使用的那一炉，同一炉可以关联多条冲煮记录。两种豆子的每克成本统一展示在豆子详情页末尾。

## 一、页面流程

| 类型 | 添加豆子时录入 | 豆子详情的操作 |
| --- | --- | --- |
| 成品豆 | 名称、产地、处理法、烘焙商、烘焙度、烘焙日期、购入克数、实付豆款。烘焙日期和实付豆款可留空 | 直接发起冲煮，查看冲煮记录；可登记这一批成品豆的养豆事件 |
| 生豆 | 名称、产地、处理法、购入克数、实付豆款。烘焙度和烘焙日期按炉填写 | 查看已用及剩余生豆克数，新增烘焙，按炉查看曲线、登记养豆事件和发起冲煮 |

- **添加豆子**先选择类型，再显示对应字段。同一款豆子再次购入时新增一个购入批次，使不同进价和库存各自对应实际购入记录。
- **烘焙**入口仅对生豆开放。从豆子详情进入时预选该批生豆，独立烘焙入口只列生豆。一批生豆可分多炉，每炉填写投豆克数、出豆克数、烘焙度和烘焙时间，并沿用现有事件打点与曲线。
- **冲煮**沿用「选方式 → 填参数 → 评风味 → 预览」，在预览页增加保存。从豆子或炉次详情发起时带入对应 ID。从首页发起时先选豆，选择生豆后必须明确选炉。生豆没有已完成批次时，页面引导先烘焙。养豆阶段仅供参考，烘焙完成即可记录冲煮。
- **历史记录**在豆子详情按豆子汇总，在炉次详情按炉次筛选。曲线页保留按豆子对比的入口，烘焙曲线标出炉号和烘焙度，冲煮记录显示所用炉号，方便比较同一批生豆的不同烘焙和冲煮结果。

## 二、数据关系与保存规则

| 现有或新增对象 | 设计 |
| --- | --- |
| `Bean` 豆子 | 一条记录代表一个购入批次。新增 `kind`，取值 `purchased_roasted` 或 `green`。复用 `weightGrams` 存购入克数，新增可空的 `purchaseCostCents` 存实付豆款，单位为人民币分。成品豆沿用豆子级烘焙度及烘焙日期；生豆在此层将两项留空 |
| `RoastBatch` 烘焙批次 | 复用 `beanId`、`greenGrams`、`outGrams`、`roastDate`、事件和曲线，新增每炉的 `roastLevel`。一个生豆购入批次对应多炉，每炉自己的烘焙度独立保存 |
| `BrewRecord` 冲煮记录 | 复用 `beanId` 和 `roastBatchId`。成品豆只填 `beanId`；生豆两者都填，其中炉次须已完成且属于所选豆子。一炉可关联多条冲煮记录，分别保留方式、参数、风味和曲线 |
| `RestEvent` 养豆事件 | 新增 `id`、`beanId`、可空的 `roastBatchId`、`type`、`occurredAt`、`note`。事件类型先支持开袋、密封或分装、养豆备注。成品豆的事件挂购入批次，生豆烘焙后的事件挂具体炉次 |

烘焙完成以保存有效的下豆时间和投豆、出豆量为准。已有烘焙导入入口也按同一规则确认炉次是否可用于冲煮和养豆。新建冲煮时沿用普通记录的时刻字段，生豆冲煮时间须在所选炉次下豆之后或同一时刻。冲煮用的豆子和炉次同时校验，编辑时按提交后的完整关联校验。

养豆天数以成品豆包装上的烘焙日期，或对应炉次的烘焙日期为起点。首页和详情采用同一套按自然日计算的口径，0–6 天为养豆期、7–21 天为赏味期、22 天起为风味衰减期。养豆状态由日期计算，养豆事件由用户登记。成品豆日期未知时显示「烘焙日期未知」，仍可记录事件和冲煮。

## 三、生豆用量与每克成本

- **生豆已用克数**等于该购入批次下有效、已完成炉次的投豆克数之和。**剩余生豆克数**等于购入克数减去已用克数。读取时按炉次汇总，由豆子接口返回 `usedGreenGrams` 和计算后的 `remainingGrams`。冲煮使用的是烘焙后的豆，生豆用量在烘焙时计入一次。历史投豆克数待核对时，已用和剩余返回空值，页面显示「库存待核对」。
- **数量校验**要求新购入批次的重量大于零，每炉满足 `0 < 出豆克数 ≤ 投豆克数`，每个购入批次累计投豆量上限为购入克数。新建、改量或导入时，后端在同一事务内锁定购入批次并校验，防止并发超用。提交期间禁用保存按钮，重复提交同一炉时沿用同一个提交标识，避免重复计入。
- **更正记录**时按修正后的投豆量重新汇总。删除误录炉次前展示将恢复的账面克数。已关联冲煮或养豆事件的炉次须先处理关联记录，防止历史失去来源。成品豆继续沿用现有剩余量录入方式。
- **每克成本**对两种豆子使用同一公式 `实付豆款 ÷ 购入克数`。例如，成品豆 200 克、60 元，显示 **¥0.3000／克**；生豆 1,000 克、120 元，显示 **¥0.1200／克**。生豆烘焙消耗会改变剩余量，每克采购成本仍以购入克数为分母。
- **成本位置**放在两种豆子的详情页末尾，展示一行「每克成本」。金额使用整数分保存，计算完成后四舍五入到小数点后四位。豆款留空时显示「未填写采购价」，明确填 0 元时显示 ¥0.0000／克。录入表单把购入克数和实付豆款放在一起。

## 四、冲煮备注的 Markdown 编辑与展示

- **录入页**在「风味备注」和「评鉴内容」的文本框旁提示支持 Markdown。用户直接输入或粘贴原文，首版支持标题、粗体、斜体、有序和无序列表、引用及段落换行。
- **保存**沿用现有字段，「风味备注」写入 `BrewRecord.flavor.note`，「评鉴内容」写入 `BrewRecord.review`。API 保存 Markdown 原文和换行，编辑已有记录时回填原文。旧记录缺少 `flavor.note` 时，展示页可读取原有的 `BrewRecord.notes`。
- **展示页**在保存前的冲煮预览和保存后的冲煮详情内，分别按各自来源渲染两个字段。预览使用当前草稿，详情使用已保存记录。两个区块复用一个跨端 Markdown 渲染组件，在 H5 和微信小程序遵循相同格式，空白字段隐藏，旧的纯文本照常显示。渲染只生成受支持的节点，原始 HTML 按文字显示。

## 五、豆仓图片

- **添加入口**在豆仓的「添加豆子」和「编辑豆子」页提供「添加图片」。成品豆和生豆都可以选填一张封面，可从相册选择，设备支持时可拍照。选中后先预览，保存前可更换或移除。
- **展示位置**在豆仓列表卡片显示缩略图，在豆子详情顶部显示封面，点击可查看大图。没有图片或加载失败时使用占位，豆子名称和库存信息仍可查看。
- **上传与保存**复用 `src/platform/image.ts` 的跨端选图能力和现有 `POST /uploads` 的 JSON 图片上传入口，为豆子图片传入用途 `bean`。保存时先上传文件，再用返回的对象键关联豆子。后端复用豆子的 `source_file_key` 保存对象键，校验该键对应当前用户的上传记录；列表和详情继续通过 `imageUrl` 读取展示地址。MinIO 返回有时效的链接时，读取豆子数据时根据对象键生成有效地址。只有旧 `imageUrl` 的历史豆子仍按原地址展示。
- **更换和移除**在保存成功后生效。上传失败时保留原封面和表单内容，可重试。保存成功后刷新豆仓列表及详情，重新打开页面时使用已保存的图片。

## 六、首页图标与圆角

| 截图标注位置 | 设计 |
| --- | --- |
| `ppCoffe` 标题 | 在标题左侧放小咖啡杯图标，外加圆形的浅色底。图标与标题垂直居中，副标题仍在下方 |
| 本周冲煮、平均风味、豆仓统计 | 三张卡统一使用现有大圆角 `--r-lg`（20 rpx）。标签旁分别配杯子、风味雷达、咖啡豆图标。数值和单位保持清晰 |
| 快速记录标题及方式卡片 | 标题左侧加记录图标。方式卡片也使用 `--r-lg`，在方式名称前放对应的器具小图标，例如滤杯、法压壶和虹吸壶。点击区域覆盖整张卡 |
| 工具标题及入口 | 标题左侧加工具图标。器具、豆仓、烘焙入口分别配磨豆机、咖啡豆、火焰图标，入口卡片沿用同一套圆角 |

首页统一使用小尺寸线性图标，沿用现有主题色，图标与文字之间留出一致间距。标题图标可用圆底，卡片内的小图标直接与文字搭配。首页局部样式使用现有圆角变量；H5 和微信小程序的窄屏下，快捷卡片与工具卡片可换行，标签、数值及入口文字完整可见。

## 七、实现顺序

1. **先落数据契约和迁移。** 在前后端补齐豆子分类、采购成本、炉次烘焙度和养豆事件。同步更新 API 文档、Mock 和全量备份导入导出。现有数据库使用增量迁移，`manage.py init-db` 的建表逻辑不足以更新既有表。新增豆子要明确类型。旧数据保留原 ID、日期和关联，缺少类型的豆子显示「待确认类型」，确认前可查看历史。确认生豆时核对购入量和历史投豆量。旧冲煮缺少炉次归属时显示「历史未指定」，可在确认后补关联。确认成品豆时，原有烘焙历史保留为历史记录，新增入口按成品豆规则处理。已确认类型且已有业务记录时，普通编辑锁定类型，避免改变历史记录和库存的含义。
2. **完成后端校验及库存汇总。** 复用 `/beans`、`/roasts`、`/brews`，在创建、改关联和导入入口执行相同的类型、归属和数量校验。养豆事件复用豆子资源层级，新增 `/beans/{beanId}/rest-events` 的列表和录入接口，支持更正或删除事件。生豆的事件请求需带炉次 ID。首页养豆摘要按成品豆或具体炉次取日期，修改豆子或烘焙批次后刷新相应统计缓存，并确保缓存按当前用户隔离。
3. **接通前端流程。** 豆仓编辑页切换类型和字段，并接入封面选图与上传。豆仓列表与详情展示图片，豆子详情按类型展示入口和末尾成本。烘焙表单补每炉烘焙度及克数校验。冲煮草稿存入 `beanId`、`roastBatchId` 和两项备注原文，预览页调用现有 `api.createBrew` 并在成功后刷新列表。在冲煮预览与详情接入 Markdown 渲染。
4. **调整首页视觉并验证两端。** 在首页接入图标和圆角，检查深浅主题和窄屏。先用 Mock 验证页面和导航，再以真实 API 验证保存、列表刷新、库存和重启后的持久化。在 H5 和微信小程序分别走一遍添加、烘焙和冲煮的适用路径。

## 八、验收场景

| 场景 | 预期 |
| --- | --- |
| 添加 200 克、60 元的成品豆，烘焙日期留空 | 可直接保存多条冲煮，详情末尾显示 ¥0.3000／克，养豆区显示日期未知。页面仅提供冲煮和养豆操作，提交该豆子的烘焙请求会被 API 拒绝 |
| 添加 1,000 克、120 元的生豆 | 未烘焙时引导先添加烘焙，显示已用 0 克、剩余 1,000 克，详情末尾显示 ¥0.1200／克 |
| 同批生豆分别投豆 300 克和 250 克，记录浅烘和中烘 | 显示两炉不同烘焙度，已用 550 克、剩余 450 克，每克成本仍为 ¥0.1200。每炉的养豆事件分别显示 |
| 分别从浅烘炉次保存两杯、从中烘炉次保存一杯 | 豆子详情可查看三杯，按炉筛选为两杯和一杯。冲煮保存后生豆剩余仍为 450 克 |
| 剩余 450 克时并发保存两笔各 300 克的烘焙，或重试同一笔保存 | 两笔不同烘焙最多成功一笔，同一笔重试只记一炉，库存最低为 150 克 |
| 生豆冲煮漏选炉次，或请求使用其他豆子的炉次 | API 返回校验错误，无新增冲煮记录 |
| 风味备注输入 `**柑橘酸**`，评鉴内容输入 Markdown 标题和两条列表 | H5 和微信小程序的预览与已保存详情均显示加粗、标题和列表。重新读取时原文及换行完整，旧纯文本记录也可正常显示 |
| 分别为成品豆和生豆添加封面，保存后重新打开豆仓 | 两条列表记录均显示缩略图，详情可查看大图。更换或移除后刷新结果一致，上传失败时已保存的原封面仍可查看 |
| 在 H5 和微信小程序打开首页，并分别检查深浅主题和窄屏 | 品牌标题、统计、快速记录和工具区域的图标清晰。统计、快捷方式和工具卡片圆角一致，文字没有裁切，各入口可正常点击 |
| 迁移旧库，或导入包含新字段的备份 | 历史记录及原有关联可读，新数据的类型、价格、每炉烘焙度与养豆事件在恢复后保持一致 |

实现入口可从 `src/domain/types.ts`、`src/pages/bean/`、`src/pages/roast/`、`src/store/useBrewDraft.ts`、`src/pages/brew/flavor/index.tsx`、`src/pages/brew/detail/index.tsx`、`src/pages/home/index.tsx`、`src/pages/home/index.scss`、`src/services/index.ts`、`backend/app/models/` 和 `backend/app/api/` 开始。
