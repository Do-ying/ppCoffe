# ppCoffe · 后端部署方案

> 面向运维/部署。接口契约见 `docs/02-接口契约.md`。
> 技术栈：**Flask 3 + SQLAlchemy 2 + MySQL 8 + Redis 7 + MinIO**。

---

## 0. 总体架构

```
                  ┌──────────────────────────┐
   微信小程序 ───▶│  Nginx / APISIX (HTTPS)   │
   （小程序端）    │  - TLS 终止               │
                  │  - /api  → gunicorn       │
                  │  - /cdn  → MinIO(可选)    │
                  └──────────┬───────────────┘
                             │  Authorization: Bearer <JWT>
                  ┌──────────▼───────────────┐
                  │   ppCoffe API (Flask)    │
                  │  gunicorn + 2~4 workers  │
                  │                          │
                  │  ├─ SQLAlchemy ──▶ MySQL 8      主数据（豆/冲煮/烘焙/曲线）
                  │  ├─ Cache      ──▶ Redis 7     元数据缓存 + 统计快照
                  │  └─ Storage    ──▶ MinIO      图片 + .alog 原文件
                  └──────────────────────────┘

  小程序端直传路径（图片流量不经过 API）：
   pickImages → POST /uploads/presign → PUT <presigned> → MinIO
```

**为什么这么切**

| 关注点 | 归属 | 理由 |
|---|---|---|
| 业务数据 | MySQL 8 | 事务、唯一约束、外键级联删除；JSON 列存曲线点 |
| 热点只读 | Redis 7 | `/methods`、`/flavor-wheel` 强缓存；`/stats/summary` 快照 |
| 大文件 | MinIO | 图片与 .alog 原文件；预签名直传，应用服务器不做中转 |
| 曲线计算 | API 进程 | 前后端同口径实现，前端即时预览、后端权威入库 |

## 1. 数据库（MySQL 8）

### 1.1 建库

```sql
CREATE DATABASE ppcoffe
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;

CREATE USER 'ppcoffe'@'%' IDENTIFIED BY '你的强密码';
GRANT ALL PRIVILEGES ON ppcoffe.* TO 'ppcoffe'@'%';
FLUSH PRIVILEGES;
```

> **必须 utf8mb4**：风味描述里会出现「🍊」「🫘」等 emoji，utf8（3 字节）会直接报错。

### 1.2 表结构要点

| 表 | 说明 | 关键设计 |
|---|---|---|
| `users` | 用户 | `openid` 唯一索引 |
| `beans` | 豆子 | `roast_date` 建索引（养豆期查询）；`origin`/`tags` 用 JSON 列 |
| `brews` | 冲煮记录 | `brew_date` + `bean_id` + `method` 建索引；`params`/`steps`/`flavor`/`images` 用 JSON 列 |
| `brew_curves` | 冲煮曲线 | **独立表**，`points` 用 JSON 列；`brew_id` 唯一。一条曲线点可达上千，不能塞进主表 text |
| `roasts` | 烘焙批次 | `events`/`phase_ratio` 用 JSON 列 |
| `roast_curves` | 烘焙曲线 | `points`（BT/ET/RoR 三通道）用 JSON 列 |
| `equipment` | 器具 | `type` 建索引 |
| `recipes` | 配方模板 | — |
| `uploads` | 对象存储文件登记 | `object_key` 建索引，便于按记录清理 |

曲线点独立成表的收益：

* 主表行窄 → 列表接口（`GET /brews`）只读摘要，不碰 JSON 大字段
* 曲线可独立分页/预加载
* 后续要做曲线聚合分析（RoR 统计、批次对比）时可直接下推 SQL

### 1.3 迁移

当前用 `db.create_all()` 建表（`python manage.py init-db`），适合首版。
后续迭代建议引入 **Alembic**（Flask-Migrate）做版本化迁移：

```bash
pip install Flask-Migrate alembic
flask --app wsgi db init
flask --app wsgi db migrate -m "init"
flask --app wsgi db upgrade
```

### 1.4 备份

```bash
# 每日全量 + binlog 增量
mysqldump --single-transaction --routines --triggers \
  -u ppcoffe -p ppcoffe ppcoffe | gzip > ppcoffe-$(date +%F).sql.gz
```

建议：每日全量 + binlog 保留 7 天，异地对象存储留一份。

## 2. Redis（可选）

Redis 在本项目里是**纯加速层，不是必需品**：

* `REDIS_URL` 未配置或连不上 → 服务自动降级为「实时计算」，接口行为不变，只是 `GET /methods` 每次现算（11 条数据，毫秒级）
* 用途：`/methods`、`/flavor-wheel` 强缓存（TTL 1h）；`/stats/summary` 快照（TTL 60s，写入后主动失效）

```bash
docker run -d --name ppcoffe-redis -p 6379:6379 \
  -v redis-data:/data redis:7-alpine \
  redis-server --appendonly yes --maxmemory 256mb --maxmemory-policy allkeys-lru
```

生产建议开 AOF 持久化 + `maxmemory-policy allkeys-lru`（缓存可丢）。

## 3. MinIO 部署方案 ★

### 3.1 为什么需要 MinIO

冲煮记录的附图（粉层状态、杯测液面）和烘焙 `.alog` 原文件属于**二进制大文件**：

* 不适合进 MySQL（会让表膨胀、备份变慢、binlog 暴涨）
* 前端不应绑定具体存储实现（契约第 5.5.3 节明确「MinIO / S3 / OSS 均可」）

MinIO 提供 S3 兼容 API，本地/私有云都能跑，将来换 OSS/S3 只改配置。

### 3.2 分桶策略

| 桶 | 用途 | 生命周期 | 访问策略 |
|---|---|---|---|
| `ppcoffe-brew` | 冲煮图片 | 永久（随记录） | 私有桶 + 预签名 GET |
| `ppcoffe-roast` | `.alog` 原文件、烘焙导出 | 永久 | 私有桶 + 预签名 GET |
| `ppcoffe-tmp` | 预签名直传的临时中转 | 30 天自动清理 | 私有 |

对象键规范（后端已按此生成）：

```
{用途}/{用户ID}/{uuid}.{ext}
例：brew/us_01M84.../a0c4c9f4....jpg
```

按「用途/用户」分段，好处是：

1. 按用户批量清理（换账号 / 注销）
2. 按记录清理（删除冲煮记录时同步删对象，代码已实现）
3. 便于用 IAM Policy 限制前缀

### 3.3 访问策略选型

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 私有桶 + 预签名 GET**（默认） | `MINIO_PUBLIC_BASE_URL` 留空，后端下发带签名的 GET URL（默认 7 天有效） | 安全，对象不公开暴露 | URL 过期后需重新签名（前端刷新时重新取即可） |
| B. 公开读 + CDN | 桶策略 `AllowPublicRead`，配 CDN 域名 | 前端展示最简单，CDN 缓存加速 | 知道 URL 就能访问（图片本身不算敏感） |
| C. 应用层图片代理 | `/api/v1/images/<key>` 由后端鉴权后回源 | 权限最严、可随时撤销 | 图片流量全部经过应用服务器，成本高 |

**建议**：图片用方案 B（公开读 + CDN，隐私风险低、体验好）；`.alog` 原文件用方案 A（私有 + 预签名）。

实现方式——方案 B 只需配：

```env
MINIO_PUBLIC_BASE_URL=https://cdn.ppcoffe.com
```

后端会拼出 `https://cdn.ppcoffe.com/ppcoffe-brew/brew/xxx.jpg`。

### 3.4 部署步骤（单机 Docker）

> **本项目实际采用的架构：S3 API 不走独立端口，而是由 nginx 在 80 端口反代。**
>
> ```
> 前端 ──► nginx:80 ──┬─ /api/*        ─► api:8000    （业务接口）
>                     └─ /*  (其余路径) ─► minio:9000  （S3 兼容 API，path-style 直通）
> ```
>
> 为什么这么设计：
>
> 1. **小程序「合法域名」只认标准端口**（80/443），自定义端口过不了审核；
> 2. 少开一个公网端口 = 少一个攻击面（9000/9001 不必在安全组放行）；
> 3. 后续接 HTTPS 只需在 nginx 这一层加证书，S3 与业务接口共用域名。
>
> **关键约束：路径与 Host 头都不能改写。** SigV4 把 `host` 和 canonical URI 一起算进签名，
> nginx 必须原样透传（`proxy_set_header Host $http_host;` + `proxy_pass ...$request_uri;`），
> 任何改写都会导致 `SignatureDoesNotMatch`。
>
> 预签名端点因此配置为 `MINIO_PUBLIC_ENDPOINT=118.190.152.29:80`
> （SDK 会把默认端口从 URL 里去掉，签名用的 host 与浏览器发出的 `Host:` 头恰好一致）。

```bash
docker run -d --name ppcoffe-minio --restart unless-stopped \
  -p 9000:9000 -p 9001:9001 \
  -v /data/minio:/data \
  -e MINIO_ROOT_USER=minioadmin \
  -e MINIO_ROOT_PASSWORD='<强密码>' \
  minio/minio:latest server /data --console-address ":9001"
```

控制台：`http://<host>:9001`（账号 `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`）
若 9001 不在安全组放行范围内，可用 SSH 隧道访问：

```bash
ssh -L 9001:127.0.0.1:9001 aliyun     # 然后本地打开 http://127.0.0.1:9001
```

建桶（用 `mc` 客户端）：

```bash
docker run --rm --network host --entrypoint /bin/sh minio/mc -c "
  mc alias set local http://127.0.0.1:9000 minioadmin '<强密码>' &&
  mc mb local/ppcoffe-brew &&
  mc mb local/ppcoffe-roast &&
  mc mb local/ppcoffe-tmp &&
  mc ilm rule add --expire-days 30 local/ppcoffe-tmp &&
  mc anonymous set download local/ppcoffe-brew   # 仅当采用方案 B
"
```

后端配置：

```env
STORAGE_DRIVER=minio
MINIO_ENDPOINT=minio:9000        # API 容器内读写走这个
MINIO_PUBLIC_ENDPOINT=118.190.152.29:80   # 预签名专用，必须是前端可达的 host:port
MINIO_REGION=us-east-1           # 显式指定，避免 SDK 联网查 GetBucketLocation
MINIO_ACCESS_KEY=ppcoffe         # 应用专用受限账号，不要用 root
MINIO_SECRET_KEY=<强密码>
MINIO_SECURE=false               # 前面有 Nginx 终结 TLS 时，后端仍走内网 HTTP
MINIO_PUBLIC_BASE_URL=            # 方案 A 留空 / 方案 B 填 CDN 域名
MINIO_BUCKET_BREW=ppcoffe-brew
MINIO_BUCKET_ROAST=ppcoffe-roast
MINIO_BUCKET_TEMP=ppcoffe-tmp
```

> `MINIO_SECURE=false` 表示后端与 MinIO 之间用内网 HTTP。**外网访问一律走 Nginx**，
> 不要把 9000 端口直接暴露到公网。
> `MINIO_PUBLIC_ENDPOINT` 与 `MINIO_ENDPOINT` 分开的原因：SigV4 签名把 Host 算进去，
> 读写用内网名、签名用外网地址，两者必须是两套客户端。

### 3.5 预签名直传流程

```
小程序                          API                           MinIO
  │  1. POST /uploads/presign      │                            │
  │  {filename, contentType}      │                            │
  │ ─────────────────────────────▶ │                            │
  │                               │ 生成 objectKey              │
  │                               │ 预签名 PUT (expire 1h)      │
  │  2. {objectKey, uploadUrl,     │ ◀────────────────────────── │
  │     publicUrl, headers}        │                            │
  │ ◀───────────────────────────── │                            │
  │                                                            │
  │  3. PUT uploadUrl (直传图片)                                  │
  │ ───────────────────────────────────────────────────────────▶ │
  │                                                            │
  │  4. PATCH /brews/{id}  {images:[{objectKey, url}]}           │
  │ ─────────────────────────────▶ │                            │
  │                               │ 只存 objectKey + url         │
```

要点：

* 图片流量 **不经过 API**，API 只做签名与登记
* 预签名有效期 1 小时（`PRESIGN_TTL`），直传完成后 API 侧只登记对象键
* 删除冲煮记录时后端同步删除对象（`DELETE /brews/{id}` 已实现）

### 3.6 高可用与生产加固

单机 MinIO 是单点，按数据重要度三档选：

| 档位 | 方案 | 适用 |
|---|---|---|
| 轻量 | 单机 Docker + 本地卷 + 定期 `mc mirror` 到异地 | 个人/小团队（**当前推荐**） |
| 标准 | MinIO 纠删码集群（4 节点起）+ 外部 etcd | 生产环境，多实例 API |
| 托管 | 阿里云 OSS / 腾讯 COS / AWS S3 | 不想自己运维；改 `STORAGE_DRIVER` 即可迁移 |

生产加固清单：

- [ ] MinIO 不直接暴露公网，统一走 Nginx + TLS，或使用内网地址 + 安全组
- [ ] `MINIO_ROOT_PASSWORD` 使用强密码；业务侧单独建 Access Key 并按前缀授权
- [ ] 开启版本控制 `mc version enable local/ppcoffe-brew`（误删可回滚）
- [ ] 定期 `mc mirror` 到异地桶或对象存储
- [ ] 磁盘挂载独立卷并纳入容量监控（见 3.7）

### 3.7 容量估算

| 项 | 单条大小 | 估算 |
|---|---|---|
| 冲煮图片（压缩后） | 200–500 KB | 每天 20 杯 → ~7 MB/天 → ~2.5 GB/年 |
| `.alog` 原文件 | 50–200 KB | 每炉 ~150 KB → ~55 MB/年 |
| 烘焙曲线点（DB） | ~2 KB/炉 | 每天 2 炉 → ~1.5 MB/年 |

一年下来对象存储增量 **< 5 GB**，MySQL 数据（含曲线 JSON）**< 200 MB**。
单机 100 GB 磁盘绰绰有余，且对象存储可随时冷备。

### 3.8 本地无 MinIO 时的兜底

后端内置 `STORAGE_DRIVER=local`：把对象写到 `backend/var/uploads/`，并暴露

```
PUT /api/v1/uploads/local/<objectKey>?signature=...
GET /api/v1/uploads/local/<objectKey>
```

让「预签名直传」的完整链路在没有 MinIO 时也能跑通（便于前后端联调与自动化测试）。
生产务必切回 `STORAGE_DRIVER=minio`。

## 4. API 服务部署

### 4.1 Docker Compose（推荐，一键起齐）

```bash
cd backend
cp .env.example .env       # 至少改 SECRET_KEY / MYSQL_PASSWORD / MINIO_ROOT_PASSWORD
docker compose up -d --build
docker compose exec api python manage.py init-db
docker compose exec api python manage.py seed      # 可选：演示数据
```

健康检查：

```bash
curl http://127.0.0.1:8000/api/v1/health
# {"ok":true,"data":{"status":"ok","database":"ok","redis":"ok","storage":"minio",...}}
```

### 4.2 裸机部署

```bash
sudo apt install python3.12 python3.12-venv mysql-server redis-server
cd /opt/ppcoffe/backend
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env && vim .env

.venv/bin/gunicorn -c gunicorn.conf.py wsgi:app
```

systemd 单元：

```ini
[Unit]
Description=ppCoffe API
After=network.target mysql.service redis-server.service

[Service]
User=ppcoffe
WorkingDirectory=/opt/ppcoffe/backend
Environment="PATH=/opt/ppcoffe/backend/.venv/bin"
ExecStart=/opt/ppcoffe/backend/.venv/bin/gunicorn -c gunicorn.conf.py wsgi:app
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

### 4.3 Nginx 反代

```nginx
server {
    listen 443 ssl http2;
    server_name api.ppcoffe.com;

    ssl_certificate     /etc/letsencrypt/live/api.ppcoffe.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.ppcoffe.com/privkey.pem;

    # 曲线点与图片可能较大
    client_max_body_size 25m;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    # 方案 B：CDN 直出 MinIO
    location /cdn/ {
        proxy_pass http://127.0.0.1:9000/;
        proxy_set_header Host $host;
    }
}
```

小程序端要求 HTTPS 且域名已在微信后台配置为合法域名。

### 4.4 鉴权模式

| `AUTH_MODE` | 说明 | 适用 |
|---|---|---|
| `wechat` | `wx.login` code → 换 openid → 签发 JWT | **生产默认** |
| `dev` | code 直接当 openid | 本地联调 |
| `none` | 不校验 token | 个人单机 / 内网自用 |

生产环境：

```env
AUTH_MODE=wechat
WECHAT_APPID=wx...
WECHAT_SECRET=...
```

令牌：access 7 天、refresh 30 天；前端在 `src/services/http.ts` 的 `TOKEN_KEY` 存 token。

| TCP | 80 | 0.0.0.0/0 | ✅ 已放行（nginx 反代：业务 API + S3 API） |
| TCP | 443 | 0.0.0.0/0 | ⏳ 后续接 HTTPS（注意与 frps 的 443 冲突，需调整 frps 或换端口） |

**3306 / 6379 / 9000 / 9001 全部未对公网放行** —— 前端只经 80 端口访问后端与对象存储。

前端配置：

```env
TARO_APP_API_MODE=real
TARO_APP_API_BASE_URL=http://118.190.152.29/api/v1
```

> 小程序正式发布还需要 **HTTPS 域名**（微信后台需配置合法域名），
> 当前只有 IP + HTTP，可在开发者工具「不校验合法域名」下联调。
> 接入域名后把 `MINIO_PUBLIC_ENDPOINT` 一并改成该域名（**含端口**，如 `api.example.com:443`），
> 预签名与 S3 反代会自动跟随。

### 6.4 MinIO：从源码构建本地镜像（已落地）

本机网络环境拉不到 MinIO 官方镜像，完整排查结论：

| 尝试 | 结果 |
|---|---|
| `docker pull minio/minio` | ❌ Docker Hub 域名被 DNS 污染（解析到 Meta / Twitter 的 IP），直连超时 |
| 换 DoH 解析（doh.pub / 1.12.12.12 / dns.alidns.com / 223.5.5.5） | ❌ 四个解析器对 Docker Hub 域名**全部**返回污染 IP（但 baidu 正常 → 针对该域名的定向污染） |
| 国内镜像源 daocloud / 1ms / rat.dev / hlmirror / nju / xuanyuan | ❌ 只代理 `library/` 官方命名空间，第三方镜像 403 / 404 / 需登录 |
| quay.io / ghcr.io / public.ecr.aws | ❌ MinIO 仓库已私有化（unauthorized） |
| 阿里云 ACR（杭州/北京/上海） | ❌ 不镜像第三方命名空间 |
| dl.min.io 官方二进制 | ❌ **410 Gone** —— MinIO 开源版已归档停维护，官方源不再提供文件 |
| 国内软件镜像站（TUNA/USTC/阿里/华为/上交等） | ❌ 未收录 MinIO |
| GitHub Releases | ❌ MinIO 仓库的 release 不带二进制资产 |
| **Alpine 社区源 `minio` 包** | ✅ **可用** —— `mirrors.aliyun.com/alpine/v3.22/community/x86_64/minio-0.20250524.170830-r5.apk`（38 MB，含正版 MinIO 服务端二进制） |

**最终方案：用 Alpine 社区源的 minio 包自建镜像**（不再需要交叉编译 Go）

> ⚠️ **实际部署时用的是「离线版」** `minio/Dockerfile.offline`：
> 构建阶段**完全不用网络**，二进制由构建上下文带入。
> 原因是实测发现 **BuildKit 构建容器内 `apk add` 会挂起**（拉 `dl-cdn.alpinelinux.org`
> 或 `mirrors.aliyun.com` 的 APKINDEX 都卡住，CPU 0.3% 空转 9 分钟无进展），
> 而宿主机上 `curl` 同一个源却是 1.2 MB/s 正常下载 —— 是构建容器的出网问题，不是源站问题。
> 离线版直接 `COPY minio /usr/bin/minio`，构建秒级完成。
> 产物二进制已上传到服务器 `/opt/ppcoffe/minio/{minio,mc}`。

```dockerfile
# backend/minio/Dockerfile（在线版：apk 安装，构建时需要网络）
FROM alpine:3.22
RUN sed -i 's|https://dl-cdn.alpinelinux.org/alpine|https://mirrors.aliyun.com/alpine|g' \
        /etc/apk/repositories \
 && apk add --no-cache minio minio-client \
 && rm -rf /var/cache/apk/*
ENTRYPOINT ["/usr/bin/minio"]
CMD ["server", "/data", "--console-address", ":9001"]
```

```dockerfile
# backend/minio/Dockerfile.offline（离线版：构建零网络依赖，★ 本次实际使用）
FROM alpine:3.22
COPY minio /usr/bin/minio
COPY mc /usr/bin/mc
RUN chmod +x /usr/bin/minio /usr/bin/mc && minio --version && mc --version
ENTRYPOINT ["/usr/bin/minio"]
CMD ["server", "/data", "--console-address", ":9001"]
```

产物版本：
* `minio 0.20250524.170830-r5` → **MinIO `RELEASE.2025-05-24T17-08-30Z`**（服务端，115 MB）
* `minio-client 0.20250521.015954-r5` → **mc `RELEASE.2025-05-21T01-59-54Z`**（客户端，32 MB）

> 注意：Alpine 的 minio-client 包把客户端装成 `/usr/bin/mcli`，离线版里重命名为 `mc`。
> 两个二进制都是 musl 动态链接的 ELF x86-64（依赖 `so:libc.musl-x86_64.so.1`），
> 所以基础镜像必须用 alpine。

**三种方案对比**

| 对比项 | Go 交叉编译 | Alpine 源在线构建 | Alpine 源离线构建 ★ |
|---|---|---|---|
| 构建机内存占用 | 峰值 1GB+（**会把 2C/1.6GB 的服务器拖进颠簸**） | 几十 MB | 几十 MB |
| 需要 Go 工具链 | 是（依赖 `goproxy.cn` 等国内代理） | 否 | 否 |
| 构建时需要网络 | 否 | **是**（本机 BuildKit 出网会挂起） | 否 |
| 需要上传二进制 | 是（115 MB） | 否 | 是（50 MB 压缩包） |
| 依赖官方镜像是否可拉 | 需要 `minio/minio` + `minio/mc` | 只需 `library/alpine` | 只需 `library/alpine` |

> ⚠️ **不要再在这台 2C/1.6GB 机器上编译 Go。**
> 2026-11-24 上午就因为交叉编译 MinIO 把整机拖入内存颠簸：
> Go linker 峰值内存 1GB+，机器只有 800MB 可用且 **swap 为 0**，
> 内核陷入不可恢复的回收循环，**sshd / nginx / MySQL 全部无法调度**
> （TCP 握手成功但 sshd 发不出 banner），**整机假死超过 4 小时**，
> 最终靠控制台重启才恢复。**根因就是 swap=0 —— 现在已补 2GB swap 并写入 `/etc/fstab`。**
> Alpine 方案彻底消除这个风险。

**服务启用**

```bash

docker compose --profile minio up -d
# 或用部署脚本一键完成（构建 + 启动 + 初始化桶）：
```

`minio-init` 会建三个桶（brew / roast / tmp）、给临时桶加 30 天生命周期规则，
并创建**只对这三个桶授权**的应用账号（不用 root 凭据跑业务）。

若要切到阿里云 OSS 等托管对象存储，把 `STORAGE_DRIVER` 设为 `minio`、
`MINIO_ENDPOINT` 指向对应 S3 兼容端点即可，**代码零改动**。

### 6.4.1 预签名直传的三个必要配置（踩坑记录）

MinIO 的 SigV4 预签名有三个约束，配错就是 403 `SignatureDoesNotMatch`：

| 配置 | 作用 | 配错的症状 |
|---|---|---|
| `MINIO_PUBLIC_ENDPOINT` | **预签名专用端点**，必须是前端能解析、且能直连的 `host:port`（如 `118.190.152.29:9000`）。SigV4 把 `Host` 计入签名，签名端点必须与客户端实际访问的地址一致 | 填容器内网名 `minio:9000` → 前端解析不了域名，直传失败 |
| `MINIO_REGION` | 显式指定区域（默认 `us-east-1`）。minio-py 的 `_get_region()` 在未指定时**会联网发 GetBucketLocation** | 不配 → 预签名接口强依赖 MinIO 实时可达，且明显变慢 |
| `MINIO_ACCESS_KEY / SECRET_KEY` | 应用专用受限账号（非 root） | 用了 root 凭据 → 与桶策略冲突 |

实现上，`MINIO_ENDPOINT`（内网读写）与 `MINIO_PUBLIC_ENDPOINT`（外网签名）**用两个 MinIO 客户端**：
前者做 `put_object` / `stat_object` 等实际 IO，后者只做本地签名计算，不产生服务端请求。

> 另外注意 minio-py 7.2.x 的 `presigned_put_object(bucket, object, expires)` **只接受 3 个参数**，
> 传 `content_type=` 会直接 `TypeError`（早期代码有这个问题，直到为 MinIO 驱动补了专项测试才暴露）。
> Content-Type 不参与签名即可，由直传请求头带上即可。

### 6.5 部署中踩到并已修复的坑

| 问题 | 原因 | 修复 |
|---|---|---|
| MySQL 容器起不来 | MySQL 8.4 已移除 `default-authentication-plugin` 选项 | 从 compose 的 command 中删除该参数 |
| nginx 反复重启 | `log_format` 不能写在 `server` 块内 | 移到 http 层级（conf.d 文件顶部） |
| nginx 报 `host not found in upstream "api"` | 启动时静态解析上游域名，容器换 IP 就失效 | 改用 `resolver 127.0.0.11` + `set $api_backend` 运行时解析 |
| pip 安装中途断流 | pypi.org 直连不稳定 | Dockerfile 改用可配置源（阿里云镜像实测快 12 倍）+ `--retries 10 --timeout 120` + BuildKit 缓存挂载 |
| 早期安装的 mariadb/redis/nginx 占用 3306/6379/80 | 与容器端口冲突 | `systemctl stop/disable` 停用原生服务，改由容器提供 |
| 在 2C/1.6GB 机器上编译 Go（MinIO）导致整机假死 | Go linker 峰值内存 1GB+，机器可用内存仅 800MB，swap 颠簸后 sshd/nginx/MySQL 全部无法调度（TCP 握手成功但 sshd 发不出 banner），**整机假死约 50 分钟**，2026-11-24 上午实测 | 改用 **Alpine 社区源自建镜像**（无需编译，构建内存占用极低）；详见 6.4 |
| MinIO 官方镜像拉不到 | Docker Hub 第三方命名空间被国内镜像源全面拒绝 + 开源版已归档（dl.min.io 410） | 用 Alpine 社区源的 `minio` 包自建 `ppcoffe/minio:alpine-20250524` |
| 预签名 URL 前端直传 403 SignatureDoesNotMatch | SigV4 把 Host 计入签名，而预签名用的是容器内网端点 `minio:9000`，前端解析不了 | 新增 `MINIO_PUBLIC_ENDPOINT`（外网 `host:port`）专用于签名，与内网读写端点分离；并显式设置 `MINIO_REGION` 让预签名离线化 |
| `presigned_put_object() got an unexpected keyword argument 'content_type'` | minio-py 7.2.x 该方法只接受 (bucket, object, expires) | 去掉 content_type 参数；为 MinIO 驱动补专项测试（此前该路径从未被覆盖） |
| 实例重启后仍假死（sshd 接受连接后立刻关闭、不发 banner） | swap 容量不足 → 开机阶段内存压力依旧，sshd 被分配到资源后随即被系统回收 | **重启必须配合补 swap**：先 `swapon` 2GB 再让业务起容器；否则重启只是把同一个问题推迟到开机阶段 |
| 整机假死 4 小时不恢复（2026-11-24 上午） | **swap 容量为 0** —— Go linker 1GB+ 内存需求直接触发内核不可恢复的回收循环 | 补 2GB swap + 写 `/etc/fstab`；并改用 Alpine 离线构建，从根上去掉编译环节 |
| `docker build` 里 `apk add` 挂起 9 分钟无进展（CPU 0.3%） | BuildKit 构建容器的出网问题（同一源在宿主机上 `curl` 是 1.2 MB/s 正常） | 改用 `Dockerfile.offline`：二进制由构建上下文带入，构建零网络依赖 |
| 预签名直传从外部超时 | MinIO 的 9000 端口未在安全组放行（阿里云 ECS 自流量回环也不通） | **S3 API 改由 nginx 在 80 端口反代**（`proxy_pass ...$request_uri` + `Host $http_host` 原样透传），对外只需开放 80 |
| 预签名直传 403 SignatureDoesNotMatch | nginx 改写了路径或 Host，与 SigV4 签名时算入的值不一致 | 路径不改写、Host 用 `$http_host` 原样透传；预签名端点用 `MINIO_PUBLIC_ENDPOINT` 指向对外地址 |

> **故障定位备忘（2026-11-24 实测）**
>
> | 现象 | 含义 |
> |---|---|
> | ping 通、22 端口 `banner exchange` **超时** | 内核活着，用户态全死（内存颠簸），服务完全没起来 |
> | ping 通、22 端口 **连接被关闭**（`kex_exchange_identification: Connection closed`） | 实例**刚重启过**，sshd 起来了但资源不足，连密钥交换都撑不住 |
> | ping 通、80 端口无响应 | nginx / Docker 容器链未恢复 |
>
> 三条路径（ssh / 浏览器 / 服务端抓取器）同时超时而 ICMP 正常，可以**排除**安全组与本地网络因素 ——
> 安全组拦截是 DROP（表现为超时）且会连 ICMP 一起挡掉。
